# scopeburn 설계안 (초안 v0.3, 2026-10-10)

> v0.2 변경: 개인 도구에서 **공개 배포용**으로 전환. 0장(경쟁·차별점), 2장(배포 형태), 5.1(기록 형식 변경 대응), 5.2(경로 일반화), 9~11장이 바뀌었다.
> 이름 `scopeburn` 확정 (2026-10-10). npm 미사용 확인, 배포 직전 다시 확인한다.

1인 개발자를 위한 **개발 진행 척도 + 토큰·비용·구독 한도** 리포트.
형태는 **Claude Code 플러그인(스킬) + 독립 CLI**다. 계산은 전부 CLI가 하고, 스킬은 실행·해석·로드맵 갱신을 맡는다.
CLI는 Claude 없이도 돌아간다 (`npx scopeburn`).

---

## 0. 경쟁과 차별점

**토큰·비용·5시간 구간 집계만으로는 새로울 게 없다.** 이미 다음 도구들이 있다.

| 도구 | 하는 일 |
|---|---|
| ccusage | 로컬 JSONL 기반 일·월·세션·5시간 구간별 비용, 실시간 소모 속도 |
| Claude-Code-Usage-Monitor | 소모 속도, 한도 도달 예상 시각 |
| ccburn | 구간 대비 소모 차트 |
| claude-burn-rate | 브랜치별 비용 |
| Cost Guardian | 훅으로 도구 호출별 비용, 작업 전 비용 추정 |

**빈자리는 "진행"과 "비용"의 연결이다.** 범위와 완료를 나란히 그리는 진짜 번업, 로드맵 항목별 비용, "남은 범위를 끝내려면 얼마·구간 몇 회"라는 예상을 하는 도구는 찾지 못했다 (2026-10-10 검색 기준).

이에 따른 원칙:
- **주력은 진행 척도(3·4장)와 항목별 비용·예상(5.3·6.5장)이다.** 토큰 집계는 이를 위한 기반일 뿐이다.
- 토큰 집계를 ccusage보다 잘 만들려고 하지 않는다. 다만 저장소·항목 귀속에는 응답별 도구 경로가 필요한데 기존 도구는 이걸 제공하지 않는다. 그래서 파서는 직접 만든다.
- 비용 숫자는 ccusage와 크게 어긋나지 않게 맞춘다. 같은 기록인데 숫자가 다르면 신뢰를 잃는다. 검증할 때 ccusage를 기준값으로 쓴다.
- 로드맵 없이 설치해도 첫 실행에서 쓸모가 보여야 한다. 그래서 `init`이 기존 문서·git 이력을 읽어 ROADMAP 초안을 만들어 준다.

## 1. 목표와 비목표

**목표**
- 범위가 늘어나는 것을 눈에 보이게 한다 (번업: 범위 선 vs 완료 선).
- 프로젝트가 지금 어느 단계에 있는지, 정해 놓고 안 한 일이 얼마나 묵었는지 보여준다.
- 토큰과 금액을 저장소·로드맵 항목·모델별로 보여준다 (API 실비, 구독 환산).
- 구독 5시간·주간 한도를 얼마나 썼는지 추정하고, 언제 닿을지와 남은 작업에 드는 양을 예상한다.

**비목표**
- "몇 % 완료" 같은 단일 진행률. 범위가 고정되지 않은 1인 개발에서는 거짓 숫자가 된다.
- 커밋 수, 코드 줄 수, 코딩 시간 같은 활동량 지표.
- 팀 기능, 클라우드 동기화, 외부 전송. 전부 로컬에서만 처리한다.

## 2. 구성과 배포

### 2.1 배포 형태
| 경로 | 대상 | 설치 |
|---|---|---|
| **Claude Code 플러그인** (주) | Claude Code 사용자 | 플러그인 마켓플레이스에서 추가 → `/scopeburn` 스킬과 CLI가 같이 들어옴 |
| **npm CLI** | Claude 없이 리포트만 보려는 사람, CI | `npx scopeburn` |
| GitHub 릴리스 | 소스 열람, 이슈 | MIT 라이선스 |

### 2.2 언어: TypeScript (Node) — v0.1의 Python에서 변경
- Claude Code 사용자는 Node가 깔려 있을 가능성이 가장 높다. Python은 특히 Windows에 기본으로 없다.
- `npx` 한 줄로 설치 없이 실행된다. 경쟁 도구(ccusage)도 같은 방식이라 사용자가 익숙하다.
- 런타임 의존성은 0개를 목표로 한다. 빌드 결과는 단일 JS 파일이다.

### 2.3 파일 배치
```
scopeburn/                          ← 소스 저장소 (공개)
  src/                             ← 파서·집계·로드맵·리포트
  dist/scopeburn.js                 ← 단일 번들 (npm·플러그인 공통)
  data/prices.json                 ← 기본 단가표 (릴리스마다 갱신)
  plugin/                          ← .claude-plugin 매니페스트, skills/scopeburn/SKILL.md
  test/fixtures/                   ← Claude Code 버전별 익명화 기록 샘플 (5.1)
  docs/  README.md  README.ko.md

<사용자 홈>/.scopeburn/             ← 실행 데이터 (OS별 홈 경로)
  config.json                      ← 작업 폴더, 플랜, 통화, 언어
  prices.override.json             ← 사용자가 단가를 덮어쓸 때
  calibration.jsonl                ← /usage 보정 기록
  cache/                           ← 집계 캐시 (숫자만)
  report.html
```

### 2.4 처음 실행 (설정 없이 동작해야 함)
- Claude 기록 폴더는 OS별 기본 위치에서 자동으로 찾는다. 환경변수로 기록 위치를 바꾼 경우도 따른다.
- 저장소 목록은 사용자가 적지 않아도 된다. 기록 안의 경로에서 git 저장소 루트를 찾아 자동으로 등록한다 (5.2).
- 플랜은 첫 실행 때 한 번 묻는다 (API / Pro / Max 등). 답하지 않으면 API 환산값만 보여준다.
- 언어는 시스템 로캘을 따른다 (한국어·영어부터).

## 3. 로드맵 형식 (`ROADMAP.md`)

### 3.1 원칙
- **상태의 원본은 `ROADMAP.md` 하나뿐이다.** `docs/작업현황.md` 같은 서술형 문서는 그대로 두되, 무엇이 끝났고 무엇이 남았는지는 ROADMAP에만 적는다. 서술형 문서는 ROADMAP을 링크한다.
- 사람이 손으로 읽고 고칠 수 있는 평범한 마크다운이어야 한다.
- 갱신은 Claude가 작업 흐름 안에서 한다 (6장). 사용자가 따로 입력하는 일은 없어야 한다.
- **번업 이력은 ROADMAP.md의 git 이력으로 만든다.** 별도 DB가 없고, 커밋할 때마다 스냅샷이 남는다.

### 3.2 문법

```markdown
# ROADMAP · <프로젝트명>
stage: beta

## <묶음 이름>
- [x] {ID} 항목 제목 ~M @decided(2026-10-01) @start(2026-10-02) @done(2026-10-07)
- [ ] {ID} 항목 제목 ~L @decided(2026-10-07) @start(2026-10-09)
  - [x] {ID.1} 하위 항목 ~S @done(2026-10-09)
- [-] {ID} 잘라낸 항목 ~M @cut(2026-10-08) — 이유 한 줄
```

| 요소 | 뜻 | 필수 |
|---|---|---|
| `stage:` | `idea` `prototype` `mvp` `beta` `released` `maintenance` 중 하나 | 파일당 1개 |
| `- [ ]` / `- [x]` / `- [-]` | 남음 / 완료 / 잘라냄 | ✓ |
| `{ID}` | 항목 고유 ID. 토큰 귀속과 이력 추적의 열쇠라서 바뀌면 안 된다 | ✓ |
| `~S` `~M` `~L` `~XL` | 크기. 번업과 예상치는 개수가 아니라 크기 점수로 센다 (1 / 2 / 4 / 8) | 없으면 `~M` |
| `@decided(날짜)` | 하기로 정한 날 | 권장 |
| `@start(날짜)` | 손대기 시작한 날. 토큰 귀속 구간의 시작 | 권장 |
| `@paused(날짜)` | 멈춘 날. 남의 심사·답을 기다리는 등 손을 놓은 상태라, 이날 뒤로는 비용을 받지 않는다 | 선택 |
| `@done(날짜)` / `@cut(날짜)` | 끝낸 날 / 자른 날 | 완료·자름 시 |

- 하위 항목이 있으면 **잎(가장 아래) 항목만** 센다. 부모는 묶음 표시용이다.
- 잘라낸 항목은 범위 선에서 빠진다. 범위를 줄인 결정도 차트에 보인다.

### 3.3 예시: T_RPG 2막 (작업현황.md와 메모리 기준, 날짜 일부는 추정)

```markdown
# ROADMAP · T_RPG
stage: beta

## 2막 v2.3 — 1차 출시 범위
- [x] {A} 2막 진입·전직(스탯 재분배) ~M @done(2026-10-06)
- [x] {B} 경험치·레벨·SP/AP, 레벨업 화면, 스킬 창 ~L @done(2026-10-07)
- [x] {C} 평판·진영 거점·의뢰 틀 ~L @done(2026-10-07)
- [x] {C.F} 파밍 필드 4종 ~M @done(2026-10-07)
- [x] {C.H} 내 은신처 1차 ~M @done(2026-10-07)
- [x] {D} 새 적 5종·보스 3종·특수 스킬 6 ~XL @done(2026-10-08)
- [x] {H} 쓰러짐→재시작, 보스 뒤 처리, 레벨 상한 30 ~M @done(2026-10-08)
- [x] {E} 메인 7장면·의뢰 13·세션/이벤트/풍경·보관소 19편 ~XL @done(2026-10-09)
- [-] {E.LM} 2막 랜드마크 10곳 ~L @cut(2026-10-09) — 이야기 지점이면 충분
- [ ] {G} 2막 밸런스 ~XL @decided(2026-10-07) @start(2026-10-09)
  - [x] {G.bot} 전체 플레이 봇 bot2/sim2 ~L @done(2026-10-09)
  - [ ] {G.boss} 2막 보스만 조정 (scrap 학습 차단 절반, cyber 교란으로 빔 반사) ~M @decided(2026-10-09)
  - [ ] {G.verify} REPLAY·sim2 재측정, 갈래 편차 ≤10%p ~M
  - [ ] {G.cyber} cyber 초반 사망 재검증 ~S
- [ ] {F} 그림: 층 나눠 덧그리기 ~XL @decided(2026-10-09)

## 다음 정규 릴리스
- [x] {R.twist} 반전 누출 가드 ~S @done(2026-10-08)
- [ ] {R.enmodel} 영어 GM 모델 암호화·새 태그 ~M
- [ ] {R.en2} 2막 영어 글 ~L
```

이 예시만으로도 리포트가 바로 보여주는 것이 있다.
- `{G.boss}`는 10-09에 결정했지만 시작하지 않은 상태다. 결정 후 묵은 날짜가 표시된다.
- `{E.LM}`을 잘라서 범위가 줄었다.

### 3.3a 3단계 구현에서 정한 것 (2026-10-10)
- **날짜 태그로 과거 상태 되살리기**: ROADMAP이 처음 커밋되기 전의 상태는 항목의 `@decided`, `@done`, `@cut` 날짜로 다시 만든다. 그래서 도입 첫날부터 번업이 그려진다. LLM은 필요 없다.
  `@decided`가 없는 항목은 가장 이른 날짜부터 있었던 것으로 본다. 3.4의 LLM 이력 채우기는 날짜 태그가 비어 있을 때만 쓰는 보조 수단이 된다.
- **날짜 태그는 모두 선택**: 태그가 없으면 git 이력에서 그 상태가 처음 나타난 스냅숏 날짜로 채운다. 태그가 있으면 태그가 우선한다.
- **ID 없는 항목도 받는다**: 제목으로 추적하고, 제목을 바꾸면 이력이 끊긴다고 한 줄로 안내한다.
  실제로 개발자의 다른 저장소(Z-V_Scan)에 있던 ID 없는 기존 ROADMAP.md(체크박스 45개)가 그대로 읽혔다.
- 코드 블록(```) 안의 체크박스는 무시한다. 부모 항목은 묶음일 뿐이고 점수에는 잎 항목만 센다.
- **첫 초안**: T_RPG(git 기록과 작업현황.md 기준)와 band-note(git 기록과 메모 기준)에 `ROADMAP.md` 초안을 만들었다. 두 저장소 모두 커밋하지 않은 상태다.

### 3.4 기존 이력 채우기 (1회)
- 처음 도입할 때는 ROADMAP의 git 이력이 없다.
- T_RPG는 `docs/작업현황.md`에 21개 커밋 이력이 있다. 스킬이 각 커밋 시점을 읽고 "그때 ROADMAP이었다면" 하는 스냅샷을 만들어 `~/.scopeburn/backfill/<repo>.jsonl`에 저장한다.
- 이 작업은 LLM이 1회만 하고, 이후로는 실제 git 이력을 쓴다.

## 4. 진행 척도

### 4.1 번업
- **범위 선**: 그 시점 ROADMAP의 (남음 + 완료) 잎 항목 크기 점수 합계. 잘라낸 항목은 뺀다.
- **완료 선**: 완료된 잎 항목 크기 점수 합계.
- 시점은 ROADMAP.md를 건드린 커밋마다 하나씩 찍는다. 같은 날 커밋이 여러 개면 그날 마지막 것을 쓴다.
- **범위 증가율**: 최근 14일 동안 범위가 늘어난 양 ÷ 완료가 늘어난 양. 1보다 크면 끝이 멀어지는 중이고, 리포트에 경고로 띄운다.

### 4.2 단계
- `stage:` 값을 프로젝트별 카드에 표시한다.
- 단계가 바뀐 날짜는 git 이력에서 뽑는다.
- 단계마다 머문 기간도 보여준다.

### 4.3 결정→구현 기간
- **완료 항목**: `@done − @decided`. 프로젝트별 중앙값을 낸다.
- **미완료 항목**: `오늘 − @decided`. "정해 놓고 묵은 일" 목록으로 띄운다.
- 시작은 했는데 멈춘 항목도 따로 잡는다 (`@start`는 있고 `@done`은 없는데 그 저장소에서 7일간 토큰 사용이 0인 경우).

## 5. 토큰·비용

### 5.1 데이터 원천
- `~/.claude/projects/**/*.jsonl`. 세션 본문과 `<세션>/subagents/agent-*.jsonl` 둘 다 읽는다.
- 쓰는 필드는 다음뿐이다. 대화 내용은 읽지도 저장하지도 않는다.
  - `type == "assistant"` 줄의 `message.id`, `requestId`, `message.model`, `message.usage`, `timestamp`, `sessionId`, `cwd`, `isSidechain`
  - 귀속용 경로: 같은 줄 `message.content`의 `tool_use` 입력 가운데 `file_path`, `path`, `command`. 경로만 추출하고 나머지는 버린다.
- **중복 제거 필수**: 같은 응답이 여러 줄로 기록된다 (실측 24,022줄 → 고유 12,327건). 키는 `(message.id, requestId)`이고, 같은 키면 마지막 줄의 usage를 쓴다.
- 증분 처리: 파일별 (크기, 수정 시각)을 캐시해 두고 바뀐 파일만 다시 읽는다. 개발자 PC 기준 기록이 364MB였다. 첫 실행 진행률을 표시한다.
- **기록 형식은 공개 규격이 아니다.** Claude Code가 업데이트되면 필드가 바뀔 수 있다. 그래서 다음 장치를 둔다.
  - 필드를 읽는 코드는 한 모듈에 모은다. 필드가 없으면 그 줄을 건너뛰고 건너뛴 개수를 리포트 하단에 표시한다. 숫자가 조용히 틀리는 것보다 "읽지 못한 기록 N건"이 낫다.
  - 기록의 `version` 필드로 Claude Code 버전별 샘플을 `test/fixtures/`에 모아 회귀 시험을 한다. 샘플은 경로와 내용을 익명화한다.
  - 읽지 못한 비율이 5%를 넘으면 "Claude Code 형식이 바뀐 것 같다, 업데이트 확인" 안내를 띄운다.

### 5.2 저장소 귀속
- 여러 저장소를 담은 상위 폴더에서 세션을 여는 사람이 많다 (개발자 본인도 기록 거의 전부가 그렇다). 그래서 `cwd`만으로는 저장소를 알 수 없고, 세 단계로 판정한다.
  0. **경로 정규화**: Windows(`E:\a\b`), Git Bash(`/e/a/b`), WSL(`/mnt/e/a/b`), macOS·Linux 경로를 같은 형태로 바꾼다. 대소문자는 OS 규칙을 따른다. 상대 경로는 그 줄의 `cwd` 기준으로 푼다.
  1. **응답 단위**: tool_use 경로에서 위로 올라가며 `.git`이 있는 가장 가까운 폴더를 저장소 루트로 본다. 결과는 캐시한다. 여러 저장소에 걸리면 경로 개수 비율로 나눈다. 지금은 없어진 폴더라면 경로 문자열만으로 묶는다.
  2. **턴 단위 전파**: 경로가 없는 응답(생각만 하거나 답변만 쓴 것)은 같은 사용자 턴(`promptId`) 안에서 가장 많이 나온 저장소를 따른다.
  3. **세션 단위 전파**: 턴에도 경로가 없으면 세션 전체에서 가장 많이 나온 저장소를 따른다. 그래도 없으면 `cwd`가 저장소 폴더인지 보고, 아니면 `(미분류)`로 둔다.
- 서브에이전트 기록도 같은 규칙을 쓰되, 경로가 없으면 부모 세션의 판정을 따른다.
- `config.json`의 `aliases`로 여러 저장소를 한 프로젝트로 묶을 수 있다. 예: 게임 본체, 모델 학습, 공개용 저장소를 한 프로젝트로.

### 5.2a 1단계 구현에서 확인한 것 (2026-10-10)
- **작업 폴더 규칙 추가**: git 저장소만 프로젝트로 보면, 개발자 기록 토큰의 23%가 미분류였다. 대부분 git이 아닌 폴더(소설 원고, 학습 데이터 폴더)에서 한 작업이었다.
  그래서 **git 저장소를 2개 이상 바로 아래에 둔 폴더를 "작업 폴더"로 보고, 그 안에 실제로 있는 하위 폴더를 프로젝트로 인정**한다. 작업 폴더 바로 아래의 낱개 파일, 점(.)으로 시작하는 폴더, `AppData` 같은 OS 폴더는 제외한다. 미분류는 4.7%로 줄었다.
- **한 응답의 중복 줄은 서로 다른 내용 조각을 담는다.** 한 줄에는 생각만, 다른 줄에는 도구 호출만 있는 식이다. usage는 마지막 줄 값을 쓰고, 경로는 모든 줄에서 모은다.
- **경로 표기 통일**: 같은 폴더가 `E:\x`와 `e:\X`로 다르게 적힌다. 디스크의 실제 표기(`realpath`)로 맞춘다. `*`, `?`가 든 글롭 패턴은 경로로 보지 않는다.
- **가져온 세션**: `entrypoint`가 없고 `version`이 `"1.0"`인 세션이 있다. 다른 곳에서 실행된 세션이 이 PC 기록으로 들어온 것으로 보인다. ccusage는 이 기록을 세지 않는다.
  scopeburn은 같은 계정의 실제 사용이라 **기본으로 포함**하고, `doctor`에 `(imported)`로 따로 표시하며, `--local-only`로 뺄 수 있게 했다. 구독 한도도 계정 단위로 깎이므로, 한도 추정(6장)에는 포함하는 쪽이 맞다.
- **ccusage 대조 결과**: `--local-only` 기준으로 24일치 입력·출력·캐시 쓰기·캐시 읽기가 일별·필드별로 정확히 일치했다. 차이는 대조 도중에도 쓰이고 있던 당일 세션뿐이었다.
- 첫 실행은 65개 파일, 7.7만 줄, 364MB를 약 6.5초에 읽는다. 이후 실행은 캐시를 쓴다.
- 캐시 형식은 파싱·귀속 규칙이 바뀔 때마다 `CACHE_VERSION`을 올려서 다시 읽게 한다.

### 5.2b 2단계 구현에서 확인한 것 (2026-10-10)
- **단가 출처는 공식 가격 페이지 하나로 한다.** Claude API 스킬 문서에는 Sonnet 5.5 캐시 읽기가 $0.20으로 적혀 있었지만, 공식 페이지는 $0.10(입력 단가의 0.05배)이었다. 공식 페이지를 따른다.
  캐시 읽기 배율이 모델마다 다르다: Fable 5.1은 0.025배, Opus 5.5와 Sonnet 5.5는 0.05배, 나머지는 0.1배. 그래서 배율 공식으로 계산하지 않고 모델별 단가를 그대로 적는다.
- 추가로 반영한 요금 규칙:
  - Haiku 5.5는 프롬프트가 10만 토큰을 넘으면 더 비싼 단가를 쓴다. 프롬프트 크기에는 캐시 읽기·쓰기 토큰도 포함된다.
  - fast 모드는 2배, `inference_geo: "us"`는 1.1배다.
  - 웹 검색은 건당 $0.01이다.
- **ccusage 금액 대조**: 9월 11일~10월 8일, 이 PC 세션 기준으로 1,201.50달러 대 1,201.51달러였다. 센트 단위까지 일치한다.
- **상태줄 설치**를 개발자 PC에 적용했다. `settings.json`에서는 `statusLine` 키만 추가됐고 다른 키는 그대로였다.
  **미확인**: 개발자는 VS Code 확장(`entrypoint: claude-vscode`)만 쓰는데, 설치 직후에는 보정 표본이 들어오지 않았다. VS Code 확장이 상태줄 명령을 실행하는지 확인해야 한다. 실행하지 않는다면 VS Code 사용자에게는 수동 `calibrate`가 주 경로가 된다. 이건 배포 문서에도 적어야 한다.
- 수동 `calibrate` 표본에는 재설정 시각이 없다. 그래서 활동 기록으로 되짚은 5시간 구간에 맞춰 넣는다. 주간 수동 표본은 재설정 시각을 알 수 없어서 한도 추정에 쓰지 않는다.

### 5.3 로드맵 항목 귀속
- 시각 t에 저장소 R에서 쓴 토큰은, 그 시각에 R의 ROADMAP에서 **진행 중인 잎 항목**(`@start ≤ t`, 완료·자름 날짜 > t)에 나눠 준다. 크기 점수 비율로 나눈다.
- 진행 중인 항목이 없으면 `(로드맵 밖)`으로 둔다. 이 비율이 높으면 "로드맵에 없는 일을 많이 하고 있다"는 신호다.
- v1은 날짜 단위로 처리한다. 같은 날 여러 항목을 오가면 정확도가 떨어진다. 이걸 정밀하게 하려면 커밋 메시지에 `{ID}`를 붙이는 규칙이 필요하다 (열린 질문 1).

### 5.3a 4단계 구현에서 정한 것 (2026-10-10)
- **배분 우선순위**:
  1. 커밋 메시지에 `{ID}`가 있으면 직전 커밋 이후 그 저장소의 사용량을 그 항목이 가져간다. 여러 ID가 있으면 크기 점수로 나눈다.
  2. 그렇지 않으면 그 시각에 진행 중인 잎 항목들이 크기 점수로 나눈다.
  3. 둘 다 아니면 "로드맵 밖"으로 둔다.
- **진행 구간**: `@start`부터 완료·자름·멈춤 중 가장 이른 날까지다. 완료 항목에 `@start`가 없으면 `@decided`부터로 본다. **잘라낸 항목은 `@start`가 있을 때만** 비용을 받는다. 시작도 안 하고 자른 일에 비용을 붙이지 않기 위해서다.
- **`@paused` 추가**: 실제로 써보니 band-note의 "카카오 채널 이전"(비즈니스 심사 대기)이 끝없이 진행 중으로 잡혀서, 9월 16일 이후 비용 271달러를 다 빨아들였다. 그래서 멈춘 날로 구간을 닫는 태그를 넣었다. 그 결과 로드맵 항목에 연결된 비율이 95%에서 57%로 바로잡혔다.
- **"로드맵 밖" 비율은 그 자체로 신호다.** T_RPG는 로드맵이 10월 6일 시작한 2막만 다뤄서 25%만 로드맵에 연결됐다. 그 전의 1막·GM 작업은 로드맵에 없기 때문이다.
- **완료 예상** = 남은 점수 × 크기 점수당 비용의 중앙값이다. 중앙값은 그 프로젝트의 완료 항목 5개 이상으로 내고, 모자라면 모든 프로젝트를 합친 값으로 대신한다.
  5시간 한도 추정치가 있으면 "5시간 구간 몇 회"도 함께 보여준다.
  초안 기준 첫 결과: T_RPG는 남은 21점 ≈ $44, band-note는 남은 27점 ≈ $309.

### 5.4 금액
- `prices.json`: 모델별로 입력, 출력, 캐시 쓰기, 캐시 읽기 단가를 적는다 (USD / 100만 토큰).
  - 캐시 쓰기는 5분형과 1시간형 단가가 다르다. usage에 둘이 나뉘어 있으면 각각, 없으면 보수적으로 1시간형 단가를 쓴다.
  - 기본 단가표는 **릴리스할 때마다 공식 가격을 확인해서 갱신**한다. 기억이나 추측으로 채우지 않는다.
  - 단가표에 없는 새 모델이 기록에 나오면 금액을 0으로 두지 않는다. "단가 미등록: <모델명>"을 띄우고, 그 모델 토큰은 금액 합계에서 빼서 따로 보여준다.
  - 사용자는 `prices.override.json`으로 덮어쓸 수 있다. 네트워크로 단가를 가져오는 기능은 넣지 않는다 (오프라인 원칙, 9장).
- 웹 검색 같은 서버 도구 호출은 `server_tool_use` 개수 × 건당 단가로 따로 더한다.
- 기본 통화는 USD다. 다른 통화는 `config.json`의 `currency`와 `rate_per_usd`(사용자가 정하는 고정값)로 표시한다. 환율을 실시간으로 가져오지는 않는다.
- **API 모드**: 이 금액이 곧 실제 지출 추정치다. API 키로 쓴 세션과 구독으로 쓴 세션이 섞여 있으면 구분해야 한다 (열린 질문 2).
- **구독 모드**: 같은 금액을 "API 환산값"으로 표시하고, 월 구독료 대비 배율("이번 달 구독료의 ×N만큼 사용")을 함께 보여준다.

## 6. 구독 한도 (5시간·주간)

### 6.1 알 수 있는 것과 없는 것
| 항목 | 로컬 기록으로 | 비고 |
|---|---|---|
| 지금 5시간 구간이 언제 시작해 언제 끝나는지 | ✓ 정확 | 첫 메시지 시각부터 5시간 |
| 이 PC의 Claude Code가 구간 안에서 쓴 양 | ✓ 정확 | |
| 한도 자체가 몇 토큰인지 | ✗ | 공개 안 됨. 모델마다 소모 속도가 다름 |
| claude.ai 웹·앱, 다른 PC에서 쓴 양 | ✗ | 같은 한도를 깎지만 기록이 없음 |

### 6.2 구간 재구성
- 모든 응답 시각을 정렬한다.
- 첫 응답에서 구간을 시작하고, 시작 + 5시간이 지난 뒤 처음 나오는 응답에서 새 구간을 시작한다.
- 주간 구간도 같은 방식으로 만든다. 주간 재설정 기준(요일·시각)은 `/usage` 화면에서 확인해서 `config.json`에 적는다.

### 6.3 소모 단위
- 한도는 모델마다 닳는 속도가 다르다. 그래서 토큰 수가 아니라 **API 환산 금액을 소모량의 공통 단위**로 쓴다.
- Opus 1토큰이 Haiku 1토큰보다 한도를 더 깎는다는 점이 단가 차이에 대략 반영된다는 가정이다. 이 가정이 맞는지는 보정 데이터로 확인한다 (6.4).

### 6.4 보정
- 사용자가 `/usage`에 보이는 5시간·주간 사용률을 스킬에 알려준다. 예: `/scopeburn calibrate 42 18`.
- 스크립트는 그 시점의 구간 소모량과 짝지어 `calibration.jsonl`에 한 줄을 쌓는다: `{ts, pct_5h, pct_week, cost_5h, cost_week, model_mix}`.
- **한도 추정치** = `cost_5h / (pct_5h / 100)`의 중앙값. 표본이 3개 미만이면 "보정 필요"로 표시한다.
- 웹·다른 PC 사용분은 추정치를 **낮추는 쪽**으로만 작용한다 (로컬 소모는 작게 잡히는데 %는 크게 나오니까). 그래서 중앙값과 함께 범위를 보여주고, 표본 간 편차가 크면 "로컬 밖 사용이 섞였을 수 있음"이라고 표시한다.
- **자동 보정 (2026-10-10 확인)**: Claude Code는 상태줄 명령에 넘기는 JSON에 `rate_limits.five_hour` / `rate_limits.seven_day`를 넣는다. 각각 `used_percentage`(0~100)와 `resets_at`이 들어 있다. 이걸로 보정을 자동화한다.
  - scopeburn이 상태줄 명령으로 들어가서 받은 값을 `calibration.jsonl`에 기록한다. 같은 값이면 쓰지 않고, 최소 1분 간격을 둔다.
  - 사용자가 이미 상태줄 명령을 쓰고 있으면 덮어쓰지 않는다. 기존 명령을 감싸서, 입력은 그대로 넘기고 출력도 그대로 돌려준다. 설치와 제거는 `scopeburn statusline install|uninstall`로 하고, 원래 설정은 백업해 둔다.
  - `resets_at`이 있으면 6.2의 구간 재구성 대신 이 값을 구간 경계로 쓴다 (정확). 주간 재설정 기준도 여기서 얻으니 사용자가 적을 필요가 없다.
  - **제약**: 구독(Pro/Max)에서만 들어오고, 세션의 첫 응답 뒤부터 들어오며, 일부 버전·계정에서는 빠진다는 보고가 있다. 그래서 필드가 없으면 조용히 건너뛰고, 수동 `calibrate` 명령을 예비로 남긴다. `resets_at` 형식(유닉스 초 / ISO 문자열)은 둘 다 받는다.
  - 상태줄은 Claude Code가 화면에 떠 있을 때만 갱신된다. 그래서 보정 표본은 실제로 쓰는 시간대에만 쌓이는데, 한도 추정에 필요한 것도 그 시간대라 문제없다.

### 6.5 예상
- **단기**: 최근 45분 소모 속도 × 남은 시간 → "이 속도면 ○○:○○에 5시간 한도 도달 (추정)". 구간이 끝날 때까지 안 닿으면 "구간 안에서 여유".
- **장기**: 남은 잎 항목 크기 점수 × 그 프로젝트의 크기 점수당 소모 중앙값 → 다음 두 가지로 환산한다.
  - "약 ○○ 달러(API)"
  - "5시간 구간 약 ○회 / 주간 한도의 약 ○%"
- 크기 점수당 소모 중앙값은 그 프로젝트의 완료 항목이 5개 이상일 때만 쓴다. 그보다 적으면 전체 프로젝트 평균으로 대신하고 그렇다고 표시한다.

| `/scopeburn init <저장소>` | ROADMAP.md 초안 생성 (기존 문서·git 이력을 읽어 항목 추출, 사용자 확인 뒤 저장) + 3.4 이력 채우기 |

**Claude가 작업 중에 지킬 규칙** (SKILL.md에 적고, 각 저장소 CLAUDE.md에서 한 줄로 가리킨다):
- 로드맵 항목을 시작할 때: `@start` 추가.
- 끝냈을 때: `[x]`와 `@done`.
- 사용자가 새로 하기로 정했을 때: 항목 추가 + `@decided`.
- 하지 않기로 했을 때: `[-]`와 `@cut`, 이유 한 줄.
- ROADMAP 변경은 그 작업의 커밋에 같이 넣는다. 따로 커밋하지 않는다. 그래야 이력과 작업이 맞물린다.

## 8. 리포트 화면 (`report.html`, 단일 파일, 인라인 SVG)

1. **전체**: 프로젝트 카드. 단계, 번업 미니 차트, 마지막 활동, 이번 주 소모(원), 경고 배지(범위 증가·묵은 결정·멈춘 항목).
2. **프로젝트 상세**:
   - 번업 차트 (범위 선, 완료 선, 잘라낸 지점 표시)
   - 항목 표 (상태, 크기, 결정→구현 기간, 소모 금액)
   - 로드맵 밖 소모 비율
3. **사용량**:
   - 현재 5시간 구간 게이지 (추정 %, 보정 표본 수, 도달 예상 시각)
   - 주간 게이지
   - 일별 소모 막대 (모델별로 쌓아서 표시)
   - 모델 배분 비율 (Opus / Sonnet / Haiku). 모델 계층 정책을 지키는지 볼 수 있다.
4. **예상**: 프로젝트별 남은 범위 → 금액·구간 수, 근거 표본 수와 함께 표시.

밝은·어두운 테마를 모두 지원하고, 숫자마다 "추정"인지 "정확"인지 표시한다.

### 8.0 5단계 구현 메모 (2026-10-10)
- `report`는 HTML 파일 하나를 만든다. 개발자 기록 기준 118KB다. `serve`는 127.0.0.1 전용이고 30초 캐시를 둔다. 데이터 재계산은 약 1.1초이고, 페이지는 1분마다 `data.json`을 다시 받는다.
- 데이터는 프로젝트·모델·가져온 세션 여부별 일 단위 합계로 넣는다. 그래서 필터는 브라우저에서 바로 계산된다. 대화 내용은 넣지 않는다.
- 시각화 기준:
  - 모델 색은 전체 모델 목록의 순서로 고정한다. 필터를 바꿔도 색이 바뀌지 않는다.
  - 쌓인 막대 사이에는 2px 간격을 둔다. 단일 계열 막대는 1번 색 하나만 쓴다.
  - 번업 범위 선은 중립색, 완료 선은 1번 색이다. 끝에 직접 라벨을 붙이고, 십자선 툴팁에는 그날 추가·완료·잘라낸 항목이 나온다.
  - 끌어서 확대하고, 더블클릭으로 해제한다.
  - 상태 색(5시간 게이지)은 아이콘·라벨과 함께 쓴다. 일별 금액은 표로도 볼 수 있다.
- **헤드리스 Edge로 확인**: 밝은·어두운 테마를 1280px에서 봤다. 좁은 폭은 Edge 창 최소 폭이 492px이라 390px을 직접 재지 못했다. 대신 492px에서 넘치는 요소를 검사했고, 가로 스크롤 상자 안의 항목 표 말고는 넘치는 게 없었다.
- **HTML 주석 안 체크박스 무시**: `init` 템플릿의 형식 설명이 항목으로 잡히던 버그를 찾아 고쳤다.
- **스킬**: `skill install`이 `~/.claude/skills/scopeburn/SKILL.md`를 이 PC의 실행 경로로 채워서 설치한다. 개발자 PC에는 설치를 마쳤다.
  배포용 플러그인은 `npm run build:plugin`으로 `plugin/`에 만들고, 그 안에서는 `npx -y scopeburn@latest`를 호출한다.
  **미확인**: 플러그인 매니페스트 형식과 마켓플레이스 등록 절차는 배포 전에 공식 문서로 확인해야 한다.

### 8.1 인터랙티브 (결정 2026-10-10)
정적 리포트가 아니라 **조작할 수 있는 대시보드**로 만든다. 그래도 파일 하나로 열리고, 외부 요청은 0을 유지한다 (데이터는 HTML 안에 JSON으로 넣는다).
- **필터**: 기간(7일·30일·전체·직접 지정), 프로젝트, 모델, 가져온 세션 포함 여부. URL 해시에 상태를 저장해서 같은 화면을 다시 열 수 있게 한다.
- **차트 조작**:
  - 번업에 마우스를 올리면 그 시점의 범위·완료 점수와 그날 추가·완료·잘라낸 항목이 보인다.
  - 구간을 끌어서 확대하고, 범례를 눌러 선을 켜고 끈다.
- **연결 이동**: 프로젝트 카드 → 상세 → 항목을 누르면, 그 항목의 비용 내역(일별·모델별)과 귀속 근거(직접 / 턴 / 세션)가 펼쳐진다.
- **표**: 열마다 정렬하고, 항목 이름으로 검색한다.
- **예상 시뮬레이션**: 남은 항목을 체크로 빼거나 넣으면 "끝내는 데 드는 금액과 구간 수"가 바로 다시 계산된다. 범위를 자를지 판단하는 용도다.
- **5시간 게이지**: `scopeburn serve`로 띄우면 로컬 서버(localhost 전용)가 일정 간격으로 다시 집계해서 갱신한다. 파일로 열었을 때는 만든 시점의 값만 보인다.
- **구현**: 외부 라이브러리 없이 바닐라 JS와 SVG로 만든다. 번들 크기를 작게 유지하고 CDN 의존을 없애기 위해서다. 차트 종류가 넷 정도(선, 막대, 게이지, 쌓인 막대)라 직접 그려도 감당할 수 있다.

## 9. 개인정보·보안 (배포 시 핵심 신뢰 요소)
- **네트워크 전송 0.** CLI는 어떤 외부 요청도 하지 않는다. 사용 통계(텔레메트리)도 없다. README 첫 화면에 적고, 코드에 네트워크 모듈을 가져오는 부분이 없음을 CI 검사로 보장한다.
- 리포트와 캐시에는 **숫자, 저장소 이름, 항목 ID만** 남긴다. 대화 내용, 명령 전문, 파일 내용은 저장하지 않는다.
- 세션 기록에는 비밀값이 들어 있을 수 있다. 파서는 경로 추출에 필요한 필드만 읽고, 나머지 문자열은 메모리에 붙잡아 두지 않는다.
- 리포트는 로컬 파일이다. 저장소 이름이 드러나니까 공유 전에 이름을 가리는 옵션(`--redact`)을 둔다.
- 버그 제보용 `scopeburn doctor`는 익명화된 형식 정보(필드 이름, 버전, 건너뛴 개수)만 출력한다. 내용은 넣지 않는다.

## 10. 구현 순서

배포 전에 개발자 본인이 먼저 써본다 (T_RPG, band-note). 개인 경로를 박아 넣지 않는 것은 처음부터 지킨다.

| 단계 | 내용 | 확인 기준 |
|---|---|---|
| 1 | 사용 기록 파서 (중복 제거, 증분 캐시, 경로 정규화, 저장소 자동 판정, 형식 변경 대응) + `/usage` 자동 읽기 가능 여부 조사 | 지난 30일 저장소별 토큰 표, (미분류) 15% 이하, 같은 기간 총액이 ccusage와 ±2% 이내 |
| 2 | 단가표 + 금액 + 5시간·주간 구간 + 보정 | 보정 3회 뒤 한도 추정치와 범위 표시 |
| 3 | ROADMAP 파서 + git 이력 번업 + 결정→구현 기간 | T_RPG 예시로 차트가 그려짐 |
| 4 | 항목별 귀속 + 장기 예상 | G단계 하위 항목별 금액 표시 |
| 5 | HTML 리포트 (한·영) + 스킬 + `init` | `/scopeburn` 한 번으로 전체가 나옴 |
| 6 | 본인 사용 3주 | 주 3회 이상 사용. 못 미치면 원인을 고치거나 접는다 |
| 7 | 배포 준비: 플러그인 매니페스트, npm 배포, README(영·한), 단가 갱신 절차, macOS·Linux·WSL 확인 | 깨끗한 환경에서 `npx scopeburn` 한 줄로 리포트가 나옴 |
| 8 | 공개 | 아래 배포 KPI 측정 시작 |

**배포 KPI** (텔레메트리가 없으니 공개 지표로만 잰다):
- npm 주간 다운로드, GitHub 별, 플러그인 설치 수 (마켓플레이스가 제공하면)
- 이슈 중 "형식 변경으로 깨짐" 비율. 높으면 5.1의 대응이 부족하다는 뜻이다.
- 질적 신호: `init` 이후 ROADMAP을 계속 쓰는지 묻는 이슈·토론 반응
